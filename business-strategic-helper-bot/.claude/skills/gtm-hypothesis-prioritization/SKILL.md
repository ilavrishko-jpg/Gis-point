# GTM Hypothesis Prioritization

## Коли застосовувати
- Команда пропонує новий сегмент, нішу, країну, канал або офер.
- Треба вирішити, які гіпотези запускати зараз, які в резерв, які закрити.
- Треба підібрати офер під сегмент або вирішити, чи потрібен новий офер.
- Треба оцінити результат тесту і вирішити: масштабувати, змінити, закрити.

## Правила бота (завжди)
1. **Не вигадуй цифри.** Кожне число позначай джерелом: `CRM` · `схожий сегмент` · `оцінка`.
   Якщо даних немає — постав оцінку, познач `оцінка` і знизь «Впевненість» (крок 3).
2. **Одна гіпотеза = одна зв'язка** (крок 1). Розмиті формулювання («Ізраїль», «телеком») — поверни на уточнення.
3. **Той, хто пропонує, не ставить собі фінальний бал.** Бот рахує, ФД валідує економіку, рішення — комітет.
4. Спершу висновок (go / малий тест / резерв / no-go), потім обґрунтування. Мова — українська.

## Алгоритм

### Крок 0. Зібрати вхідні дані
Запитай або знайди (якщо чогось бракує — продовжуй, але познач прогалину у виході):
| Дані | Звідки | Навіщо |
|---|---|---|
| Виграні/програні угоди за 12–24 міс. (сегмент, чек, маржа, цикл, джерело, причина) | CRM | Реальні конверсії і профіль найкращого клієнта |
| Каталог оферів (крок 4) | Продажі / Євген | Підбір оферу |
| Вільна capacity: SDR-години, LinkedIn-профілі, delivery-люди за компетенціями | RevOps, delivery | Стоп-фактор і портфель |
| Активні гіпотези та їхній статус | Трекер гіпотез | Ліміт і портфель |
| Мінімальний чек і цільова маржа | ФД | Стоп-фактор і економіка |

### Крок 1. Сформулювати гіпотезу
Формула (усі 5 полів обов'язкові):
> **Сегмент × Роль ЛПР × Біль/Тригер × Офер × Канал**

Приклад: «Геодезичні фірми DACH 20–200 людей × Head of Operations × виграли тендер і не
вистачає людей на обробку × аутстаф команди обробки за 2 тижні × LinkedIn + email за сигналом тендеру».

Джерела кандидатів (у порядку надійності):
1. Кластери виграних угод з CRM («ще таких самих клієнтів»).
2. Суміжні сегменти до виграних (той самий біль, інша галузь або країна).
3. Сигнали/тригери: тендери, фінансування, наймання, виставки, нові контракти.
4. Запити з ринку та від партнерів.
5. Ідеї команди без даних.

**Правило новизни.** Порахуй, скільки з 5 полів нові для компанії (ще не продавали):
- 0–1 нове → **Core**;
- 2 нові → **Adjacent**;
- 3+ нові → **Bet**. Для Bet запропонуй розбити на 2–3 гіпотези з меншою кількістю нових полів —
  інакше провал тесту не пояснити.

### Крок 2. Стоп-фактори (так/ні)
Будь-яке «ні» → статус **Blocked** + що треба, щоб зняти блок. Далі не рахуй.
| # | Питання |
|---|---|
| G1 | Можемо виконати зараз або ≤1 міс. (є люди потрібної компетенції)? |
| G2 | Можемо дістатися до ЛПР (є канал, контакти, мова)? |
| G3 | Немає юридичного бар'єру (передача даних, ліцензії, резидентство, санкції)? |
| G4 | Очікуваний чек ≥ мінімального порогу ФД? |
| G5 | У сегменті є бюджет на такі послуги? |

### Крок 3. Скоринг
Кожен параметр 1–5, бал групи = середнє, фінальний бал = зважена сума.

| Група (вага) | Параметр | 1 бал | 5 балів |
|---|---|---|---|
| **A. Ринок (30%)** | Досяжні акаунти | < 100 | ≥ 500 |
| | Гострота болю | «було б добре» | must-have, дедлайн або штраф |
| | Видимі тригери | немає | регулярні, відстежувані |
| | Конкуренція | червоний океан, лише ціна | мало нішевих гравців |
| **B. Право на перемогу (30%)** | Кейси в сегменті | немає | ≥ 2 з цифрами |
| | Ресурси delivery | треба наймати | є вільні люди |
| | Доступ до каналу | лише холодний | теплий: партнер, асоціація, наявний клієнт |
| | Мова, регіон, пояс | бар'єри | без бар'єрів |
| **C. Економіка (30%, валідує ФД)** | Чек на рік | нижче середнього | вище середнього |
| | Валова маржа | < цільової | ≥ цільової |
| | Повторюваність | разовий проєкт | довгий аутстаф, повторні замовлення |
| | Час до перших грошей | > 9 міс. | ≤ 3 міс. |
| | Вартість тесту / очікуваний прибуток | висока | низька |
| **D. Стратегія (10%)** | Вихід на суміжні сегменти | немає | відкриває 2–3 ніші |
| | Відповідність позиціонуванню | розмиває | підсилює |

**Контрольний фінансовий розрахунок (від ФД):**
```
Валовий прибуток 12 міс = акаунти × конверсія в угоду × чек × маржа
Фін. бал = (Валовий прибуток × Впевненість) / Вартість тесту (гроші + години × ставка)
Впевненість: CRM цього сегмента 0,7–0,8 · схожий сегмент 0,5 · оцінка 0,3
Якщо перші гроші > 9 міс. → Фін. бал × 0,7
```

**Рішення** (окремо за скорингом і за фін. балом):
| Статус | Скоринг | Фін. бал |
|---|---|---|
| **Go** — у чергу на запуск | ≥ 3,8 | ≥ 3 |
| **Малий тест** — 100 акаунтів, мінімальний бюджет | 3,0–3,8 | 1–3 |
| **Резерв / No-go** — вказати, що має змінитись | < 3,0 | < 1 |

Якщо скоринг і фін. бал дають різні статуси — бери нижчий і поясни розбіжність.

### Крок 4. Підібрати офер з наявних
Для кожної гіпотези зі статусом Go або Малий тест оціни **кожен офер каталогу** (1–5):
| Критерій | Питання |
|---|---|
| Відповідність болю | Закриває саме біль/тригер цієї гіпотези? |
| Докази | Є кейс, референс, цифри результату саме для цього типу клієнта? |
| Готовність delivery | Можемо почати за ≤ 2 тижні? |
| Маржа | ≥ цільової (ФД)? |
| Легкість входу | Є малий перший крок: пілот, аудит, тестове завдання? |

- **Бал оферу ≥ 4,0** → беремо як є.
- **3,0–4,0** → беремо з адаптацією: інший кейс, вхідний крок, мова болю сегмента. Сам офер не змінюємо.
- **< 3,0 у всіх оферів** → **прогалина оферу**, крок 5.

**Каталог оферів — стартовий, з рішень зустрічі 2026-09. Команда має верифікувати і доповнити:**
| Офер | Тип | Для кого (гіпотетично) |
|---|---|---|
| Аутстаф GIS/обробки даних | Core | Геодезичні фірми, Ізраїль, компанії без сигналів |
| Аутсорс обробки даних / проєкт | Core | Геодезія, мобільне мапування |
| Автоматизація опрацювання картографічних даних | Adjacent | Геодезія, картографія |
| Консалтинг з автоматизації core-процесингу (ПМ + CTO + інженер) | Adjacent | Середні й великі геодезичні та мапінг-компанії |
| Аналіз підземних комунікацій (utility) | Adjacent | Utility, цивільний сектор |
| GIS + IT для SaaS-платформ телекомів | Bet | Телеком |
| AI-помічник для картографа | Bet | SaaS-платформи |
| R&D-офіс в Україні | Bet | Компанії, що масштабують розробку |
| Офіс / юрособа в країні клієнта | Опція до оферу | Клієнти з обмеженнями на передачу даних |

### Крок 5. Сформувати новий офер (тільки для пріоритетних)
Новий офер створюється **лише** якщо гіпотеза має статус **Go** (скоринг ≥ 3,8 і фін. бал ≥ 3).
Для Малого тесту — лише адаптація наявного.

Збирай з наявних модулів, а не з нуля: команда, процес, інструмент, кейс. Побудуй драбину:
1. **Вхідний крок** — пілот, аудит, тестове завдання: малий, швидкий, з фіксованою ціною.
2. **Core** — основна послуга.
3. **Розширення** — довгий аутстаф, підтримка, автоматизація.

Шаблон картки оферу:
```
Назва:
Для кого (сегмент × роль):
Біль / тригер:
Результат у цифрах (для клієнта):
Формат і вхідний крок:
Модель ціни (fixed / T&M / підписка / ексклюзив-премія):   ← ФД
Цільова маржа:                                              ← ФД
Докази (кейси, цифри):
Зняття ризику (гарантія, пілот, SLA, захист IP/ексклюзивність):
Хто виконує (delivery-власник) і коли може почати:
Чим відрізняємось від 2 головних конкурентів:
```
Новий офер не запускається без полів «Модель ціни», «Маржа» і «Хто виконує».

### Крок 6. Портфель і capacity
1. Відсортуй гіпотези Go і Малий тест за фінальним балом.
2. Розподіли capacity SDR і LinkedIn-профілів: **70% Core · 20% Adjacent · 10% Bet**.
3. Одночасно **не більше 3 активних тестів**. Нова гіпотеза з вищим балом витісняє найслабшу активну.
4. Позначай кожну гіпотезу: `cash engine` (гроші зараз) або `growth vehicle` (ставка), див. `cash-acceleration`.

### Крок 7. Дизайн тесту
- 100–200 акаунтів · 2–3 варіанти меседжу · 4–6 тижнів.
- Пороги фіксуються **до старту**, за конверсіями з CRM (не за чужими бенчмарками):
  позитивні відповіді → зустрічі → кваліфіковані ліди → угоди.
- Перед стартом: кейс, 1–2 пости/статті в LinkedIn, картка оферу заповнена, власник призначений.
- Бюджет тесту (гроші + години) затверджений ФД.

### Крок 8. Рев'ю і рішення
Після 100 акаунтів або 4–6 тижнів порівняй план і факт, заміни «оцінку» фактом і перерахуй бал.
| Що бачимо | Де проблема | Дія |
|---|---|---|
| Мало відповідей | Сегмент, роль, тригер або меседж | Змінити роль або тригер, офер не чіпати |
| Відповіді є, зустрічей немає | Офер | Повернутись до кроку 4/5 |
| Зустрічі є, кваліфікованих лідів немає | Портрет клієнта | Звузити сегмент або розмір компаній |
| Ліди є, угод немає | Ціна, докази, delivery | Пілот, кейс, ціноутворення (ФД) |
| Пороги виконано | — | **Scale**: перевести в Core, збільшити capacity |

Не більше 2 ітерацій на одну гіпотезу. Після двох провалів — **Closed** із записом причини.

## Ролі
| Роль | Відповідальність |
|---|---|
| Власник сегмента | Формулює гіпотезу (крок 1), дає оцінки груп A і B, відповідає за pipeline у $ |
| Аналітик / RevOps | Конверсії з CRM, capacity (кроки 0, 7, 8) |
| ФД | Мінімальний чек, маржа, група C, фін. бал, бюджет тесту, модель ціни оферу |
| Комітет (CEO + ФД + власники сегментів) | Раз на тиждень, 30 хв: go / no-go, портфель 70/20/10 |
| Бот | Проводить кроки 1–8, рахує бали, готує вихід, логує рішення |

## Калібрування 50→100
- **Зараз, ~50 людей:** одна Google-таблиця трекера гіпотез і один 30-хв комітет на тиждень.
  Скоринг достатньо робити в самій таблиці, окремий документ на гіпотезу не потрібен.
- **Ближче до 100:** власник на кожен сегмент (телеком, геодезія, ніші) з окремим pipeline
  і міні-P&L. Квартальний перегляд каталогу оферів і ваг скорингу за фактичним win/loss.
- **Анти-бюрократія:** картка гіпотези вміщується в один рядок таблиці. Ніяких погоджень,
  окрім комітету. Якщо рев'ю пропущено 2 тижні поспіль — гіпотеза автоматично на паузі.

## Вихід
Для кожної гіпотези — один рядок трекера:
```
ID | Гіпотеза (5 полів) | Тип: Core/Adjacent/Bet | Стоп-фактори | A | B | C | D | Скоринг |
Фін. бал | Впевненість + джерело | Статус | Офер (наявний / адаптований / новий) | Бал оферу |
Власник | Бюджет тесту | Пороги | Дата рев'ю
```
Плюс коротке резюме:
1. Топ-3 гіпотези до запуску і чому.
2. Що в резерві і що має змінитись, щоб запустити.
3. Прогалини в оферах (крок 5) і в даних (крок 0).
4. Розподіл capacity 70/20/10 після рішення.
