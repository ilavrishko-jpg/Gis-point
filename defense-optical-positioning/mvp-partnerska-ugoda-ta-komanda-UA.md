## Частина 1. Пункти майлстоуну M1 (чек-лист)

Майлстоун M1 = **польотно-перевірений інтегрований прототип (TRL 4 → 6)**.
Вважається досягнутим, коли всі пункти нижче закриті й задокументовані.

**Ворота (Definition of Done):**
- [ ] **П1.** Зібраний самодостатній корисний вантаж (обчислювач + камера + IMU) літає на цільовій платформі.
- [ ] **П2.** Позиціонування працює **на борту в реальному часі, GPS фізично вимкнено** (≥5 Гц, затримка < 200 мс).
- [ ] **П3.** **Абсолютна точність тримається** проти RTK-еталона: медіана ≤ 10 м (ціль ≤ 5 м; 95-й перцентиль ≤ 15 м).
- [ ] **П4.** Повторюваність: ≥ 8 вильотів · ≥ 3 типи рельєфу · ≥ 2 висоти · день.
- [ ] **П5.** Відома межа стійкості — де система деградує, задокументовано (не сюрприз).
- [ ] **П6.** Готовий **повторюваний протокол тесту + звіт**, який може прогнати третя сторона.
- [ ] **П7.** **Валідація від кінцевого користувача:** лист про зацікавленість / підтвердження тесту (підрозділ або інтегратор) — ≥ 1.

**Головне число M1 (яке команда дивиться щотижня):**
> медіана абсолютної похибки позиції (м), GPS-denied, на борту, у реальному часі. Старт 5–10 (лаб.) → тримати ≤10 у полі.

**Робочі пункти по спринтах (проміжні ворота):**
- [ ] **S1 (тиж. 1–7) «Зібрати коробку»:** вибрано і зібрано залізо; алгоритм портовано на edge; готові карта району + RTK-рig. → *Пруф на стенді: алгоритм крутиться на борту на записаних даних у потрібному темпі.*
- [ ] **S2 (тиж. 8–15) «Літати коробкою»:** контрольовані вильоти; налаштування фʼюжну; межа стійкості. → *медіана ≤10 м на ≥5 вильотах, ≥2 типи рельєфу.*
- [ ] **S3 (тиж. 16–22) «Довести і показати»:** повна матриця вильотів; демо при кінцевому користувачі; звіт; LOI; заявка на IP. → *закриті всі П1–П7.*

## Частина 2. Що узгодити з партнерами ДО старту (партнерська угода)

Це закривається однією зустріччю партнерів і фіксується письмово (навіть 1 сторінка + підписи).

### 2.1. Грошові внески — коли складаємось, скільки, хто
- [ ] **Модель внесків:** транш на **початок кожного спринту** (S1 / S2 / S3), а не одразу вся сума.
- [ ] **Сума траншу = кошторис спринту.** Орієнтовний повний кошторис MVP (уточнити): залізо `___`, полігон/оренда `___`, підрядники `___`, ПЗ/ліцензії `___`, резерв 20% `___` = **разом `___`**.
- [ ] **Розподіл внеску між партнерами:** пропорційно часткам `___%` / `___%` / … *(або рівними — узгодити).*
- [ ] **Спільне казначейство:** окремий рахунок проєкту, **2 підписи** на витрату понад `___`.
- [ ] **Правило несплати:** якщо партнер не вносить транш — механізм `розмиття частки` (pay-to-play) або конвертація у борг за ставкою `___`. Зафіксувати заздалегідь, щоб не сваритися по факту.
- [ ] **Що НЕ з каси проєкту:** особисте залізо, ноутбуки тощо — окремо або як внесок за оцінкою `___`.

### 2.2. Як рахувати особистий час (щоб не було непорозумінь)
- [ ] **Погодинна ставка кожного партнера** узгоджена наперед (blended, «внутрішня», не ринкова): партнер-керівник `___` грн/год, партнер-інженер `___` грн/год, тощо.
- [ ] **Щотижневе логування годин** у спільному трекері (ClickUp/таблиця): дата · задача · години · спринт. Без запису — година не зараховується.
- [ ] **Очікуваний мінімум залученості** на кожного (наприклад `___` год/тиж), щоб не було «пасивних співзасновників».
- [ ] **Тільки годинник у межах узгодженого скоупу** зараховується; понаднормовий скоуп — за окремим погодженням.
- [ ] **Звірка раз на місяць** + підпис обох сторін під підсумком годин (закриває майбутні суперечки).
- [ ] **Куди йдуть накопичені години:** оберіть одне — (а) **відкладена компенсація** (виплата після залучення фінансування) або (б) **sweat-equity** (конвертація годин × ставка у частку за формулою `___`).
- [ ] **Стеля/чесноти:** зафіксувати верхню межу нарахувань за час до першого зовнішнього фінансування, щоб не «роздути» борг проєкту.

### 2.3. Термін виготовлення MVP і тестування (зафіксувати дати)
- [ ] **MVP готовий до польотів (hardware+software інтеграція):** дата `___` *(орієнтир: кінець S1–початок S2)*.
- [ ] **Тестування завершене (звіт підписано, П1–П7 закриті):** дата `___` *(орієнтир: кінець S3)*.
- [ ] **Хто власник дедлайну виготовлення:** `HW-lead ___`; **хто власник тестування:** `COO / тест-директор ___`.
- [ ] **Що робимо, якщо зрив терміну:** правило перегляду (переносимо scope, а не якість воріт) — узгодити.

### 2.4. Ролі партнерів, зокрема Олександра (потрібно визначити разом)

## Частина 3. (Підзадача) Хто потрібен у проєкті для реалізації MVP

Мінімальна команда, щоб закрити M1. «Є» = маємо · «Найняти» = розрив · «Підрядник» = разова/часткова.

| # | Роль | Навіщо для MVP | Статус |
|---|---|---|---|
| 1 | **Продукт/CEO** | Бачення, BD, кінцевий користувач, гроші/гранти | Є (`___`) |
| 2 | **COO / тест-директор** | Полігон, дозволи, план тестів, звіт | Є (`___`) |
| 3 | **CV / алгоритми** | Володіє алгоритмом зіставлення (поточні 5–10 м) | Є (`___`) |
| 4 | **Embedded / real-time SW** | Порт на edge, TensorRT, латентність, фʼюжн, fail-safe | **Найняти — ключовий розрив** |
| 5 | **Hardware / електроніка** | Інтеграція вантажу: живлення, зʼєднання, синхронізація | Найняти / підрядник |
| 6 | **Механіка / інтеграція** | Кріплення, віброізоляція, тепловідведення | Підрядник (може поєднати з №5) |
| 7 | **Геопросторовий / дата-інженер** | Референс-карта + RTK ground-truth пайплайн | Є — сильна сторона GIS-Point |
| 8 | **Пілот БПЛА / польовий оператор** | Легальні вильоти, польова робота | Найняти / підрядник |
| 9 | **Юрист/IP + грант-менеджер** | Заявка на IP, кодифікація, гранти | Частково / підрядник |

**Пріоритет найму №1:** позиція **№4 (embedded/real-time)** — це найтонше місце всього MVP і найдовший у пошуку інженер. Закривати першим тижнем S1.
