# 08 · Критерії приймання, етапи впровадження, відкриті питання

   (таблиця істинності 3.8).

### Етап 2 — Механізм чек-листів (P0, ядро)

10. Завантаження seed-контенту A–G ([док. 07](./07-checklist-templates-seed.md)).

### Етап 3 — Автоматизації P0 + gate-логіка

12. Gate A / Gate B compute-поля + блокування переходів.
13. Дедуп компанії по домену (A-16).

## 8.2. Критерії приймання (Definition of Done)

### Дані та стадії
- [ ] Модуль `gis_crm` встановлюється й оновлюється (`-i`, `-u`) без помилок на чистій Odoo 18 CE.
- [ ] Усі поля-дельта з [док. 03](./03-data-model-and-fields.md) створені з правильними типами, обов'язковістю на стадії, `tracking` на ключових.
- [ ] Стадія `Nurturing` присутня тільки в Lead-пайплайні; статуси акаунта — на Contact.
- [ ] `post_init_hook` коректно проставив `account_status` наявним Contact за таблицею істинності.

### Чек-листи (ключове)
- [ ] CL-1…CL-8 з [док. 04](./04-checklist-engine.md), 4.1 виконані й перевірені сценаріями.
- [ ] Вхід у стадію створює інстанс чек-листа; повторний вхід не дублює.
- [ ] Незаповнений обов'язковий чек-лист-гейт блокує перехід з переліком пунктів (укр.).
- [ ] Відповідь на пункт із `target_field` пише значення в поле картки (і навпаки при генерації).
- [ ] Head of Sales редагує/додає/вимикає пункти в UI без розробника; зміна не ламає закриті інстанси (версійність, `question_snapshot`).
- [ ] Прогрес чек-листа видно на формі та в канбані.

### Автоматизації та гейти
- [ ] A-01: Won/Lost при `open=0, won≥1` → Contact у Farming з власником, `next_action_date` за тиром і задачею AM за 3 роб. дні.
- [ ] A-02/A-03: Contact ≥ Customer неможливо зберегти без owner/status/майбутньої дати; cron 07:00 формує звіт «Сироти».
- [ ] Gate A: будь-яке «Ні» → авто-Lead-Lost; «Не з'ясовано» блокує тільки Presale.
- [ ] Gate B: 3/3 → конвертація дозволена; 2/3 → пропозиція Nurturing; ≤1 → пропозиція Lost.
- [ ] A-06/A-07/A-08: Contract без згоди ОПР, Won без Feedback, Lost без причини/дати — заблоковані.
- [ ] Коло Фази 3 замикається: Churned через 180 днів автоматично → Farming.

### Ролі та аналітика
- [ ] Групи та record rules з [док. 06](./06-scoring-analytics-roles.md); тільки Head of Sales редагує шаблони чек-листів.
- [ ] Orphan Rate вимірюється; ціль < 2% видно у звіті.
- [ ] Головний KPI AM «% Farming → нова угода за 6 міс» доступний як Pivot.

### Якість
- [ ] Unit-тести на: A-01 (усі рядки таблиці істинності), гейти переходів, генерацію/мапінг чек-листів, cron-и (ідемпотентність).
- [ ] Демо-сценарій наскрізь: інвайт → Lead → Gate A → Presale/Gate B → конвертація → Discovery(ТЗ) → Proposal → Contract → Project → Won(відгук) → Farming → новий Lead.

## 8.3. Тест-сценарій «наскрізний» (для приймання)

1. Webhook accepted → Lead у New (дедуп по LinkedIn ID).
2. Дозаповнення + ICP Tier → Communication. Чек-лист Gate A з'явився.
3. Відповіді Gate A усі «Так» → `icp_gate_a_passed=True`. Одну поставити «Ні» → Lead авто-Lost (перевірити), відкотити.
4. Presale: чек-лист Gate B. 2/3 «Так» → спроба конвертації блокується з пропозицією Nurturing. Довести до 3/3 → конвертація.
5. Конвертація: якщо домен існує → чіпляється до наявного Contact (A-16).
6. Discovery: чек-лист ТЗ, без файлу перехід далі заблоковано. Заповнити → Proposal.
7. Contract: без `dm_approved_proposal` — блок (A-06). Поставити → Project.
8. Won: без Client Feedback — блок (A-07). AM знімає відгук → Won.
9. A-01: після Won (єдина угода) Contact → Farming, з'явилась задача AM + чек-лист «план розвитку».
10. Симулювати 180/365/+180 днів (зміна дат + cron) → Win-back → Churned → назад Farming.
11. Zero-Orphan: очистити `next_action_date` у Farming-контакта → cron 07:00 дає його у звіт «Сироти».

## 8.5. Що свідомо НЕ автоматизуємо (щоб не роздувати Odoo)

- Детальний Project Management виконання — Plane/трекер (v1.1 §14). Odoo тримає
  лише контрольні точки стадії `Project`.
- Sequence-повідомлення LinkedIn Helper — трекінг відкладено (v1.1, Етап 4).
- Збір і збагачення бази (Sales Navigator/Apollo/Clay/Snov.io) — поза Odoo.
- Окрема воронка реактивації **не потрібна**: достатньо 4 статусів на Contact +
  логіки «новий Lead» (відповідь на §13.2 №5 базового ТЗ).
