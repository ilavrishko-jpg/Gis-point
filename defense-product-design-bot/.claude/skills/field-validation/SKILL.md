# Field Validation (Фаза 4)

## Коли застосовувати
Є прототип — час перевірити на людях і в умовах. Запити: «як протестувати», «чи готово до релізу»,
«мало доступу до операторів», «як зміряти, що працює». Протокол тесту — `references/degraded-first-field-test.md`.

## Принципи
1. **Реальний оператор > думка команди.** Одна сесія з людиною, що була в полі, вартує десятка внутрішніх суперечок.
2. **Обмежений доступ — не виправдання.** Якщо прямий доступ до фронту складний: проксі-респонденти
   (ветерани, інструктори, суміжники), але чесно познач розрив і закладай ризик.
3. **Тестуй у середовищі, а не лише в переговорці.** Degraded-умови треба відтворити: планшет, ніч, офлайн, рукавиці.
4. **Стрес змінює поведінку.** Там, де можливо, додай навантаження/таймінг — «спокійний» тест приховує проблеми.

## Алгоритм
1. **Сплануй тест:** гіпотези (що саме перевіряємо з ворот Фази 2–3), задачі оператору, критерії провалу.
2. **Обери формат під доступ:** модеровані сесії, тест «завдання на час», проксі-респонденти — максимум з кожної сесії.
3. **Відтвори degraded-умови** на реальному/наближеному залізі (не лише десктоп-Figma).
4. **Збери метрики:** час виконання задачі, помилки/близькі до помилок, покриття mission flow, суб'єктивне навантаження.
   Де прямих даних нема — проксі-метрики, явно позначені.
5. **Розбери результати:** критичні usability-проблеми (блокують місію) vs косметика. Пріоритет — критичні.
6. **Реши ворота:** виправити критичне АБО свідомо прийняти ризик з підписом власника.

## Чек-ліст фази (ворота 4→5)
- [ ] Проведено тест з реальними операторами або наближеним проксі (зафіксовано хто/скільки/умови).
- [ ] Критичні usability-проблеми виправлені або прийняті власником з ризиком.
- [ ] Підтверджено роботу в degraded-умовах на реальному/наближеному залізі.
- [ ] Є проксі-метрики там, де доступ обмежений (позначені як проксі).
- [ ] Зібрано перелік відомих обмежень для реліз-нотаток.

## Шаблон — Звіт валідації (1 стор.)
```
ЩО ПЕРЕВІРЯЛИ (гіпотези):
З КИМ / УМОВИ (кількість, роль, залізо, degraded так/ні, проксі так/ні):
ЗАДАЧІ ОПЕРАТОРУ:
МЕТРИКИ (час / помилки / покриття / навантаження):
КРИТИЧНІ ПРОБЛЕМИ → рішення (fix / accept-ризик, власник):
ВІДОМІ ОБМЕЖЕННЯ (у реліз-нотатки):
ВЕРДИКТ: готово до Deliver? так / ні / так-з-ризиками (перелік)
```

## Вихід
**Звіт валідації + список змін + вердикт готовності.** Відкриває (чи ні) ворота у Фазу 5.
