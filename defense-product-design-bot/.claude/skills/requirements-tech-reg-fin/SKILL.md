# Requirements: Tech · Reg · Fin (Фаза 2 · специфікація вимог)

## Коли застосовувати
Після синтезу опитувань, коли треба перетворити інсайти на конкретні вимоги. Йде поруч із
`product-definition-prioritization`: PRD дає «що і чому», ця навичка — інженерно-регуляторно-фінансовий зріз.

## Кроки
1. Згрупуй вимоги: **технічні · регуляторні · фінансові**.
2. Кожній вимозі — **джерело** (інсайт/регуляція/економіка). Без джерела не потрапляє в must.
3. Пріоритезуй за **MoSCoW**: Must / Should / Could / Won't (зараз).
4. Додай **критерій приймання** — як перевіримо (вимірювано).
5. Познач **регуляторні блокери** — без чого продукт не можна виводити (кодифікація, ліцензія ОВТ, частоти, класифікація даних).

## Шаблон
```
| # | Група (тех/рег/фін) | Вимога | MoSCoW | Джерело | Критерій приймання | Залежність |
Регуляторні блокери (без цього не запускаємось): ___
Відкриті питання: ___
```

## Доменні орієнтири
- **Технічні:** дальність, навантаження, час польоту, стійкість до РЕБ, навігація без GPS, серійність.
- **Регуляторні:** кодифікація NCAGE/NSN, допуск Міноборони, ліцензія ОВТ, частоти УДЦР, ДСТУ, експортний контроль,
  класифікація/безпека даних; для експорту — ATO/STIG/FedRAMP (US), interoperability/STANAG (НАТО).
- **Фінансові:** цільова ціна, мінпартія, собівартість, локалізація %, потужність/міс, обіговий капітал.

## Degraded-first перевірка
Серед must-вимог явно зафіксуй degraded baseline (офлайн/ніч/стрес) — щоб він став вимогою, а не побажанням.

## Чек-ліст (доповнює ворота 2→3)
- [ ] Кожна must-вимога має джерело і критерій приймання.
- [ ] Регуляторні блокери виявлені й мають власника.
- [ ] Degraded baseline закладено як вимогу.

## Вихід
Специфікація вимог (must/should/could) → разом із PRD живить Фазу 3 (Design) і Фазу 5 (Compliance).
